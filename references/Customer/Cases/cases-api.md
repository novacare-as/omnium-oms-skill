# API Reference

Source: https://docs.omnium.no/docs/Customer/Cases/cases-api

> Public API endpoints for managing cases — create, search, update, assign, change status, and delete, with the update rules, errors and case events.

## Endpoints

| Method | Endpoint | Description |
| --- | --- | --- |
| `GET` | `/api/cases/{id}` | Get a case by ID |
| `POST` | `/api/cases` | Create a new case |
| `PUT` | `/api/cases` | Replace a case. See [Updating Cases](cases-api.md#updating-cases) |
| `PATCH` | `/api/cases` | Partial update (only non-null fields are applied) |
| `DELETE` | `/api/cases/{id}` | Delete a case (soft delete) |
| `POST` | `/api/cases/search` | Search cases with filters and pagination |
| `POST` | `/api/cases/{id}/assignto` | Assign a case to a user |
| `POST` | `/api/cases/{id}/changestatus` | Change the status of a case |

All endpoints require authentication. `GET` and search need the `CaseRead` or `CaseAdmin` role. Create, update, patch, delete, assign and change status need the `CaseAdmin` role. See [roles](../../GettingStartedWithAPI/api-developer-guide.md).

The public API has no endpoints for notes, attachments or reply templates. Agents write notes in the Omnium UI, and customer replies arrive through [inbound email](cases-inbound-email.md) or SMS.

The full case model returned by GET and search endpoints:

| Field | Type | Description |
| --- | --- | --- |

| `Subject` | string | Case title |
| `Description` | string | Case description |
| `Status` | string | Current status |
| `Priority` | string | Current priority |
| `Source` | string | Case origin. Omnium sets `Email`, `Sms` or `Order`; any other value can be given |
| `AssignedToUserId` | string | Assigned agent's user ID, which is the Omnium user's email address |
| `AssignedToName` | string | Assigned agent's display name |
| `CustomerId` | string | Linked customer ID |
| `CustomerName` | string | Customer display name |
| `CustomerEmail` | string | Customer email address |
| `Tags` | string\[\] | List of tags |
| `RelatedOrders` | string\[\] | Linked order IDs |
| `RelatedCustomers` | string\[\] | Linked customer IDs |
| `RelatedProjects` | string\[\] | Linked project IDs |
| `RelatedCarts` | string\[\] | Linked cart IDs |
| `RelatedSkuIds` | string\[\] | Related SKU IDs |
| `RelatedProductIds` | string\[\] | Related product IDs |
| `Participants` | OmniumCaseParticipant\[\] | Case participants. Not shown in the UI and not notified |
| `CaseNotes` | OmniumComment\[\] | Public case notes (the thread with the customer) |
| `InternalNotes` | OmniumComment\[\] | Internal notes (staff only) |
| `Properties` | OmniumPropertyItem\[\] | Custom properties |
| `CaseStatusLog` | OmniumCaseStatusLogItem\[\] | When the case first reached each status |
| `FollowUpDate` | DateTime? | Follow-up date. Omnium sends no reminder |
| `ResolvedDate` | DateTime? | When the case was resolved. See [Dates](cases-management.md#dates) |
| `ClosedDate` | DateTime? | When the case was last closed |
| `LastCommentDate` | DateTime? | Date of the last comment (UTC) |
| `LastCommenterName` | string | Name of the last commenter |
| `CommentCount` | int | Total number of comments |
| `Created` | DateTime | Creation timestamp (UTC). Set by Omnium |
| `Changed` | DateTime | Last modification timestamp (UTC). Set by Omnium |
| `MarketId` | string | Market ID |
| `MarketGroupId` | string | Market group ID |

### OmniumCaseParticipant

| Field | Type | Description |
| --- | --- | --- |
| `Name` | string | Participant display name |
| `Email` | string | Participant email |
| `CustomerId` | string | Optional linked customer ID |

### OmniumCaseStatusLogItem

The status log has one entry for each status the case has been in. A status the case returns to is not logged again.

| Field | Type | Description |
| --- | --- | --- |
| `Status` | string | Status name |
| `Timestamp` | DateTime | When the case first reached the status |
| `DurationSincePreviousMs` | long? | Milliseconds since the previous entry in the log (null for the first entry) |

## Creating Cases

When you create a case, Omnium sets:

| Field | Value |
| --- | --- |
| `Id`, `CaseNumber` | Always generated. Values in the request are ignored |
| `Created`, `Changed` | The current time |
| `Status` | When empty: **Status New**, or the status with the lowest level when **Status New** is not set |
| `Priority` | When empty: the **Default Priority** |
| `AssignedToUserId`, `AssignedToName` | When empty: the caller, when the caller is an Omnium user with an email address. An API client without one leaves the case unassigned |

Creating a case sends no case notification. Omnium does not check that the status, priority or tags are configured in the [case settings](cases-config.md), so use the names exactly as they are configured.

## Updating Cases

### PUT Replaces the Whole Case

`PUT` stores the case as you send it. A field you leave out is cleared, including `CaseNotes`, `InternalNotes`, `CaseStatusLog`, `CaseNumber`, `Created`, `ResolvedDate` and `ClosedDate`. The case's store is always cleared, because the public model has no store field. To change a case with `PUT`, read it with `GET` first and send the whole case back. Note text is cleaned of HTML that can run script or change styles.

Adding a note to `CaseNotes` or `InternalNotes` with `PUT` stores it on the case, but sends no email or SMS, does not update `CommentCount`, `LastCommentDate` or `LastCommenterName`, and raises no note event.

### PATCH Model

Use PATCH for partial updates. Only non-null fields are applied:

| Field | Type | Description |
| --- | --- | --- |
| `Id` | string | **Required.** Case ID to update |
| `Subject` | string | Updated subject |
| `Description` | string | Updated description |
| `Status` | string | Updated status. See [Changing Status](cases-api.md#changing-status) |
| `Priority` | string | Updated priority |
| `Source` | string | Updated source |
| `AssignedToUserId` | string | Updated assigned agent's user ID |
| `AssignedToName` | string | Updated assigned agent's display name |
| `CustomerName` | string | Updated customer name |
| `CustomerEmail` | string | Updated customer email |
| `CustomerId` | string | Updated customer ID |
| `Tags` | string\[\] | Replaces the tags |
| `RelatedOrders` | string\[\] | Replaces the related order IDs |
| `RelatedCustomers` | string\[\] | Replaces the related customer IDs |
| `RelatedProjects` | string\[\] | Replaces the related project IDs |
| `RelatedCarts` | string\[\] | Replaces the related cart IDs |
| `RelatedSkuIds` | string\[\] | Replaces the related SKU IDs |
| `RelatedProductIds` | string\[\] | Replaces the related product IDs |
| `Participants` | OmniumCaseParticipant\[\] | Replaces the participants |
| `Properties` | OmniumPropertyItem\[\] | Replaces the custom properties |
| `FollowUpDate` | DateTime? | Updated follow-up date |
| `MarketId` | string | Updated market ID |
| `MarketGroupId` | string | Updated market group ID |

A list you send replaces the whole list on the case: to add a tag, send all the tags the case should have. Because null means "leave unchanged", PATCH cannot clear a field. `keepExistingCustomProperties` is not supported for cases.

Use PATCH for most updates. It's safer — you won't accidentally clear fields you didn't intend to change. See the [PATCH patterns section](../../GettingStartedWithAPI/api-developer-guide.md#updating-resources-patch) in the API Developer Guide for details.

### Changing Status

Use `POST /api/cases/{id}/changestatus?status=...` to change the status. Only this endpoint:

*   Sets `ClosedDate` when the case moves to **Status Closed**
*   Sets `ResolvedDate` the first time the case moves to one of the two highest status levels (except **Status for Cases in Progress**)
*   Sends [case notifications](cases-notes-and-communication.md#case-notifications)
*   Raises the `CaseStatusChanged` event

A status set with `PUT` or `PATCH` only changes the field and adds the status to the status log, and a case created with `POST` in a closing status gets no closed or resolved date. No endpoint checks that the status is one of the configured statuses.

### Assigning

`POST /api/cases/{id}/assignto?userId=...&userName=...` assigns the case. `userId` is the Omnium user's email address. `userName` is optional: when it is left out, Omnium uses the user's first and last name. Assigning sends case notifications and raises the `CaseAssigned` event.

## Searching Cases

### OmniumCaseSearchRequest

| Field | Type | Description |
| --- | --- | --- |
| `SearchText` | string | Free-text search across the subject, case number, customer name, customer email and tags. Near matches are found too. The description is not searched |
| `Status` | string | Cases with exactly this status. Upper and lower case must match |
| `Priority` | string | Cases with exactly this priority. Upper and lower case must match |
| `AssignedToUserId` | string | Cases assigned to this user (the user's email address, exact match) |
| `Tags` | string\[\] | Cases that have any of these tags |
| `CustomerId` | string | Cases where this is the customer, or one of the related customers |
| `OrderId` | string | Cases linked to this order |
| `DateFrom` | DateTime? | Cases created on or after this time |
| `DateTo` | DateTime? | Cases created on or before this time |
| `SortOrder` | string | Sort field and direction |
| `Page` | int | Page number, starting at 1. `0` also gives the first page |
| `Take` | int | Results per page (default: 20) |
| `IncludeDeleted` | bool | Include soft-deleted cases (status `Deleted`) |

### Sort Options

| Value | Description |
| --- | --- |
| `CreatedAscending` / `CreatedDescending` | Sort by creation date |
| `ChangedAscending` / `ChangedDescending` | Sort by last modified date |
| `StatusAscending` / `StatusDescending` | Sort by status |
| `PriorityAscending` / `PriorityDescending` | Sort by priority severity |
| `SubjectAscending` / `SubjectDescending` | Sort by subject |
| `CustomerNameAscending` / `CustomerNameDescending` | Sort by customer name |
| `AssignedToNameAscending` / `AssignedToNameDescending` | Sort by assignee name |
| `FollowUpDateAscending` / `FollowUpDateDescending` | Sort by follow-up date |

### Facets

The search response includes `Facets` with the 10 most common values of `status`, `priority` and `assignedTo` (the user ID) among the matching cases, with a count for each.

## Deleting Cases

`DELETE` sets the case's status to `Deleted`. The case is left out of searches unless `IncludeDeleted` is `true`, but `GET` still returns it. `DELETE` returns `200 OK` also when no case has the ID.

## Errors

| Status | When | Body |
| --- | --- | --- |
| `400` | The ID, the request body or (for change status) the status is missing | A plain-text message, for example `Case id is required` or `Search request is required` |
| `404` | No case has the ID | Empty for `GET`, otherwise the text `Case not found` |
| `500` | The request failed | A plain-text message, for example `Could not search cases. Please try later` |

## Events

Case changes raise events that [event subscribers](../../Integrations/events.md) can receive. The events have the `className` `Case` and carry the case number as the object number, with the case's status, market, store and tags.

| ID | Event | Raised when |
| --- | --- | --- |
| `170100` | CaseCreated | A case is created, in any channel |
| `170101` | CaseStatusChanged | The status changes through change status: **Set to**, the AI assistant, the change status endpoint, the first agent reply or a reopen |
| `170102` | CaseAssigned | A case is assigned in the case view, by the AI assistant or with the assign endpoint |
| `170103` | CaseCommentAdded | A public note is added in Omnium or from an inbound email or SMS |
| `170105` | CaseDeleted | A case is deleted |
| `170106` | CaseInternalNoteAdded | An internal note is added |

The internal API (`265100`–`265106`) and the public API (`365100`–`365105`) also log their own case operations. See the [operation ID reference](../../Integrations/events.md#complete-operation-ids-reference).

## Code Examples

### Create a Case

```
POST /api/cases
Content-Type: application/json

{
  "Subject": "Order arrived damaged",
  "Description": "Customer reports that package was visibly damaged on arrival. Items inside may be affected.",
  "Priority": "High",
  "Source": "Phone",
  "CustomerEmail": "customer@example.com",
  "Tags": ["Shipping", "Product Issue"],
  "RelatedOrders": ["ORD-10542"]
}
```

### Search Cases

```
POST /api/cases/search
Content-Type: application/json

{
  "SearchText": "damaged",
  "Status": "New",
  "Priority": "High",
  "SortOrder": "CreatedDescending",
  "Page": 1,
  "Take": 20
}
```

Response:

```json
{
  "Result": [
    {
      "Id": "abc123",
      "CaseNumber": "CS-1042",
      "Subject": "Order arrived damaged",
      "Status": "New",
      "Priority": "High",
      "CustomerName": "Jane Smith",
      "Created": "2026-03-15T10:30:00Z"
    }
  ],
  "TotalHits": 1,
  "Facets": [
    {
      "FacetType": "status",
      "Facets": [ { "Name": "New", "Count": 1 } ]
    }
  ]
}
```

### Partial Update (PATCH)

```
PATCH /api/cases
Content-Type: application/json

{
  "Id": "abc123",
  "Priority": "Critical",
  "Tags": ["Shipping", "Product Issue", "Escalated"]
}
```

### Assign a Case

```
POST /api/cases/abc123/assignto?userId=agent@yourcompany.com&userName=John%20Agent
```

### Change Status

```
POST /api/cases/abc123/changestatus?status=In%20Progress
```
